# PRD 고도화 프로토콜 (`/prd [이름]`)

**목표**: `/docs/prd/[이름].PRD.md` 경로에 논리적으로 완결된, MECE(상호 배제와 전체 포괄) 원칙을 준수하는 제품 요구 사양서(PRD)를 작성합니다.
**제약 사항**: 🛑 **코드를 작성하지 마십시오.** 기능을 구현하지 마십시오. 오직 요구사항 엔지니어링에만 100% 집중하십시오.

## 워크플로우 단계

1.  **초기화**:
    -   명령어에서 `[이름]`을 추출합니다.
    -   `/docs/prd/[이름].PRD.md` 파일이 존재하는지 확인합니다.
    -   존재하지 않을 경우: 표준 템플릿(문제 정의, 목표, 사용자 스토리, 데이터 모델, 예외 케이스)을 사용하여 새 파일을 생성합니다.
    -   존재할 경우: 기존 내용을 읽어들입니다.

2.  **MECE 오디트 (논리 심문)**:
    -   현재 초안에서 논리적 빈틈을 분석합니다. 스스로에게 질문하십시오:
        -   누락된 에지 케이스가 있는가? (예: 네트워크 실패, 권한 부족, 빈 상태)
        -   데이터 관계가 모호한가? (예: 삭제 시 연쇄 삭제 규칙)
        -   모든 상태(로딩, 에러, 성공)에 대한 UI 동작이 정의되었는가?
        -   범위가 MECE한가? (사용자 흐름에 중복되거나 누락된 부분이 없는가?)

3.  **비판적 대화**:
    -   사용자에게 "깐깐한 질문 리스트"를 제시합니다.
    -   *예시*: "사용자가 포스트를 삭제할 수 있다고 하셨는데, 댓글도 같이 삭제되는지 명시되지 않았습니다. 연쇄 삭제 규칙이 무엇인가요?"
    -   사용자의 답변을 **기다립니다**.

4.  **내용 누적 및 합성**:
    -   사용자의 답변을 바탕으로 `/docs/prd/[이름].PRD.md` 파일을 **업데이트/고도화**합니다.
    -   단순히 대화 내용을 추가하는 것이 아니라, 공식 사양서의 각 섹션에 맞게 내용을 체계적으로 합성합니다.

5.  **루프 검증**:
    -   2~4단계를 반복합니다.
    -   더 이상 논리적 빈틈을 찾을 수 없을 때만 "최종 확정" 단계로 진행합니다.

6.  **최종 확정**:
    -   사용자에게 최종 승인을 요청합니다.
    -   파일 최상단의 상태를 `[APPROVED]`로 변경합니다.

## 템플릿 구조

```markdown
# [기능 이름] PRD
상태: [DRAFT | REVIEW | APPROVED]

## 1. 문제 정의
...

## 2. 주요 사용자 흐름 (Happy & Unhappy Paths)
...

## 3. 데이터 모델 및 스키마
...

## 4. UI/UX 상태 정의 (로딩, 에러, 빈 상태 등)
...

## 5. 비기능적 요구사항
...

## 6. 논리적 사양 및 동작 정의 (해결된 질문들)
- [x] 질문 1...
```
